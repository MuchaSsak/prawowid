# EUvsDisinfo MCP server
How to pull EUvsDisinfo articles and disinformation cases, our known-incidents corpus (scenario I, bonus "match to known incidents"). (sources: sources/2026-11-21-euvsdisinfo-mcp-api-docs.txt (current API doc, last modified 2026-05-04), sources/2026-11-21-euvsdisinfo-mcp-connect-guide.txt (claude.ai connector guide, version 2026-05-05), sources/2026-11-21-euvsdisinfo-mcp-how-to.pdf (older July 2025 how-to))

- **Endpoint:** `https://mcp.euvsd.info/mcp`. MCP over **streamable HTTP**, JSON-RPC 2.0, spec 2025-03-26+. The old how-to's host `euvsdisinfo-mcp-server.vercel.app` is **superseded**: it still answers 401 but is no longer in the docs. An intermediate host (`phpstack-1415503-5765398.cloudwaysapps.com`, Dec 2025 guide) is also old. Health check, no auth: `GET https://mcp.euvsd.info/health` → `{"status":"ok","authRequired":true,...}` (checked 2026-11-21: up; an unauthenticated POST gives 401 / -32001 "API key required"). **Our token works on the new host** (2026-11-21, user ran a stateless `tools/call cases` with `?key=`: HTTP 200, SSE `event: message` with case data). The earlier 401s came from the old host.
- **Auth:** API key, checked in this order: `?key=<token>`, `Authorization: Bearer <token>`, `X-API-Key: <token>`. Missing or invalid key → HTTP 401, JSON-RPC -32001. **Getting a key:** per the connector guide, the token is **generated by the user on https://euvsdisinfo.eu/** (a "generate it here" link in the guide). The About page (https://euvsdisinfo.eu/about/, section "MCP") also says access is "by request only" for researchers, developers, media and civil society. The organizer gave us a token too (Discord). (source: user, 2026-11-21; euvsdisinfo.eu/about) **Never commit it.** Keep it in `.env` as `EUVSDISINFO_TOKEN`.
- **Headers on every call:** `Content-Type: application/json`, `Accept: application/json, text/event-stream` (otherwise 406).

## Two modes
1. **Stateful:** `initialize` POST (no `mcp-session-id`), body `{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"prawdowid","version":"0.0.0"}}}`. Read the **`mcp-session-id` response header**. The body arrives as SSE (`event: message` / `data: {...}`). Later calls send that header. Optional `DELETE` ends the session. A bad session id → 400.
2. **Stateless (simpler, what claude.ai uses):** skip `initialize`, send any client-generated `mcp-session-id` with a direct `tools/call`. The server handles it in a one-off transport. Good enough for our bulk ingest.

## Tools
- `cases` `{limit 1..100, offset ≥0}` (both required), newest first. Results in `result.structuredContent` with `total, offset, limit, currentPage, totalPages, hasNextPage`, plus a text copy in `content`.
- `articles` `{limit 1..100, offset ≥0}`, sorted by date.
- `search` `{query (≥3 chars), date_from?, date_to? (YYYY-MM-DD)}`: full text over articles and cases. Returns `[{type: article|claim_review, title, content, link}]`. **New:** could serve as a live lookup at check time, next to the bulk index.
- `narratives` `{date_from?, date_to?}`: aggregated disinformation narratives, `[{narrative, date}]`. No params = all.

Pagination: `offset = (page - 1) * limit`. Loop while `hasNextPage`.

Errors: 401/-32001 bad key, 406/-32000 Accept header, 400/-32000 bad session, 500/-32603 backend (Elasticsearch, WordPress REST). Tool errors (e.g. bad date) come back as JSON-RPC errors.

## Data
- **Cases** (19,873 on 2026-11-21): `id` (uuid), `title`, `claim` (the disinformation claim), `fact` (EUvsDisinfo's debunk), `date` (unix seconds), `keywords[] {_id,title}`, `countries[] {_id,title}`, `linksToDisinformation[] {url, archiveUrl, snapShotURL, headLine, language{id,name}, type}`, `url` (the euvsdisinfo.eu/report/... page).
- **Articles** (6,800+): `id`, `title`, `content` (HTML→text), `dateGmt`, `keywords`, `categories`, `articleLanguage[] {slug,name}`, `thumbnailURL`, `url`. Multilingual (e.g. Romanian), so they suit multilingual retrieval.

## How we use it
- Matching a case = "this narrative has appeared in pro-Kremlin disinformation, according to EUvsDisinfo" → **shown as context or a warning, never on its own as a verdict** ([rules/hard-constraints.md](../rules/hard-constraints.md)). The case's `fact` field plus its links could later serve as secondary-source evidence, with the citation (not implemented; would need a decision).

### Built (2026-11-21): packages/core/src/narratives
A layer separate from `connectors/` (evidence), so its output can never become a citation, reach the assessment model or move a verdict.
- `euvsdisinfo/client.ts`: stateless MCP client (key in the `Authorization` header, never the URL; SSE or JSON bodies; one retry on transient errors), `search`, `listCases`, `listArticles`, and `caseToIncident` / `articleToIncident` mapping into our `KnownIncident` row (id, title, claim, fact, url, date, keywords, countries, outlet languages, **outlet hosts** for future link matching).
- Matchers (`NarrativeMatcher`, one interface). Per catalog the **first available one** in `NARRATIVE_MATCHERS` runs:
  1. `euvsdisinfo_corpus`: our own index (`KnownIncidentStore`, passed as `CoreDeps.incidents`). Runs as soon as the store holds records. Memory store today (keyword); **Supabase store later** (hybrid FTS + pgvector; the `IncidentQuery.embedding` slot is ready).
  2. `euvsdisinfo_live`: MCP `search` with the claim's `search_query_en`, cases only (`claim_review`), at most 2. **Conservative keyword filter** (`narratives/score.ts`): at least 2 shared distinctive words and at least 50% of the claim's terms, because a wrong "known disinformation" note next to a true claim would mislead.
- In `runCheck`: runs in parallel with evidence retrieval (6 s connector timeout, so no added latency in the normal case). Output: `context_matches` on the claim (additive contract field), one `known_narrative` warning, its route in `routes` (always optional; never triggers the "not all sources" caveat), a `context_match` event in the log. A claim with only a match and no evidence stays `brak wystarczających dowodów`.
- `scripts/euvsdisinfo-pull.ts`: resumable bulk pull of all cases (`--articles`, `--max`) into gitignored `data/euvsdisinfo/*.jsonl` of `KnownIncident` rows + `meta.json` (counts, avg ms per page). The input for the Supabase loader.
- `test/live/smoke-euvsdisinfo.ts`: prints the raw `search` payload, the matcher output and one cases page with timings.
- **Measured live (2026-11-21, user ran the smoke test):** `search` returns `{"results":[{type,title,content,link}]}`; `content` is **WordPress HTML** (now stripped by `htmlToText`); hits mix `article` and `claim_review`. One `search` call took 1.5 s (well inside the 6 s timeout). "Poland sends troops to Ukraine" → 2 matches, both the same narrative (score 0.75): "Poland plans to send military units to Ukraine, take control of the Western regions" and "Poland wants to occupy Western Ukraine". A cases page of 100 took 0.87 s; **total 19,873 cases**, so a full pull is about 199 pages (≈3-4 min with the 200 ms pause).
- Tests: `test/narratives_test.ts` (context never a citation or model input, verdict unchanged, weak matches dropped, no key / rejected key, corpus takes over, SSE parsing, mapping).

### Upgrade path once the DB exists (Idea)
1. Table `corpus.known_incidents` (KnownIncident columns + `embedding vector(1024)` for bge-m3 + a `tsvector` on title/claim/fact), server-only like the rest of `corpus` ([decision 001](../decisions/001-private-logs-schema.md)).
2. A loader from the pull JSONL, then a weekly incremental pull (newest first, stop at a known id).
3. A Supabase `KnownIncidentStore` doing hybrid search (FTS + vector, RRF) with the claim embedding. Pass it as `CoreDeps.incidents`: the corpus matcher takes over automatically, the live one stays the fallback.
4. Match submitted URLs against `outlet_hosts` (a link from an outlet already in cases), and try Polish queries against the multilingual embeddings.
5. Re-tune the relevance threshold with the eval set (false "known narrative" notes are the cost to watch).
